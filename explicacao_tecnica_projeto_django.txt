 GUIA TECNICO DO PROJETO DJANGO
QUIZ EDUCACIONAL - ESTRUTURA, SINTAXE E FUNCIONAMENTO

1. O que este projeto é

Este projeto e um site feito com Django, em Python.
Ele implementa um quiz educacional com:
- cadastro e login de usuarios
- login com Google
- partidas com 20 perguntas
- pontuacao e ajudas
- historico persistido no banco
- ranking semanal e mensal
- temas visuais por usuario
- compra de tema premium

Em termos tecnicos, ele e um sistema web server-side renderizado:
- o backend em Django recebe a requisicao
- processa a regra de negocio
- consulta o banco de dados
- devolve HTML pronto para o navegador

3. O papel de cada pasta e arquivo

O arquivo "manage.py" e o ponto de entrada do Django para comandos de desenvolvimento.
Exemplos:
- iniciar servidor
- criar migrations
- aplicar migrations
- rodar testes

Sintaxe comum:

python manage.py runserver
python manage.py migrate
python manage.py test

Explicacao:
- "python" executa o interpretador
- "manage.py" e o script controlador do projeto
- "runserver", "migrate" e "test" sao subcomandos do Django

- config/wsgi.py

4. Como o Django organiza o sistema

O Django trabalha com uma separacao muito forte entre:
- configuracao do projeto
- modelos de dados
- regras de negocio
- templates HTML
- URLs

No seu projeto, isso aparece assim:

- settings.py = configuracao global
- models.py = estrutura dos dados
- views.py = logica do sistema
- urls.py = roteamento
- templates/ = interface HTML

Uma boa forma de explicar isso em apresentacao e:
"O Django recebe a URL, escolhe uma view, a view usa os models se precisar falar com o banco, depois devolve um template renderizado."


5. Como a requisicao percorre o sistema

Exemplo de fluxo real:

1. O usuario acessa "/ranking/".
2. O Django verifica "config/urls.py".
3. Essa URL e encaminhada para "quiz/urls.py".
4. Em "quiz/urls.py", a rota "/ranking/" aponta para "views.ranking".
5. A funcao "ranking" em "quiz/views.py" consulta o banco.
6. Ela monta um "context", que e um dicionario com dados para a pagina.
7. O Django renderiza "quiz/templates/ranking.html".
8. O navegador recebe o HTML final.

Fluxo resumido:

URL -> urls.py -> view -> model/consulta -> template -> HTML


6. Explicando a sintaxe de URLs

Em "config/urls.py", existe algo assim:

path('admin/', admin.site.urls)
path('accounts/', include('allauth.urls'))
path('', include('quiz.urls'))

Explicacao tecnica:

- "path(...)" cria uma rota.
- O primeiro argumento e o caminho da URL.
- O segundo argumento e o destino daquela URL.

Analise linha por linha:

1. path('admin/', admin.site.urls)
   A URL "/admin/" aponta para o painel administrativo do Django.

2. path('accounts/', include('allauth.urls'))
   Tudo que comeca com "/accounts/" vai usar as rotas prontas da biblioteca django-allauth.

3. path('', include('quiz.urls'))
   A raiz do site e entregue para o arquivo de rotas do app quiz.

Agora em "quiz/urls.py" existe sintaxe como:

path("login/", views.login_view, name="login")

Explicando:

- "login/" e o trecho da URL
- "views.login_view" e a funcao Python chamada quando alguem acessa essa rota
- 'name="login"' da um nome interno para a rota

Esse nome permite usar funcoes como:
- reverse("login")
- redirect("login")

Ou seja, o sistema pode encontrar a URL pelo nome da rota sem precisar escrever "/login/" manualmente em todo lugar.


7. Explicando a sintaxe de views

Em Django, uma "view" normalmente e uma funcao que recebe um objeto "request" e devolve uma resposta HTTP.

Exemplo de assinatura:

def login_view(request):

Explicacao:

- "def" define uma funcao em Python
- "login_view" e o nome da funcao
- "request" representa a requisicao HTTP recebida

Dentro de uma view, aparecem comandos como:

return render(request, "login.html", context)

Isso significa:

- "render" monta uma resposta HTML
- "request" leva informacoes da requisicao atual
- "login.html" e o template a ser usado
- "context" e um dicionario com dados para a pagina

Tambem aparecem redirecionamentos:

return redirect("home")

Isso manda o navegador para a rota nomeada como "home".


8. Explicando decoradores usados nas views

O arquivo "quiz/views.py" usa decoradores como:

@require_POST
@csrf_exempt

Decorador em Python e uma funcao aplicada em cima de outra funcao, usando a sintaxe com "@".

8.1. @require_POST

Exemplo:

@require_POST
def iniciar_partida(request):

Significado:
- essa view so aceita requisicoes HTTP do tipo POST
- se alguem tentar acessar por GET, o Django bloqueia

Isso e util para acoes que alteram estado, como:
- iniciar partida
- ativar tema
- comprar tema

8.2. @csrf_exempt

Exemplo:

@csrf_exempt
def webhook_mercado_pago(request):

Significado:
- essa view fica dispensada da verificacao padrao de CSRF
- isso foi necessario porque um webhook externo nao envia o token CSRF do formulario do navegador

Observacao tecnica:
isso deve ser usado com cuidado. No seu caso, a seguranca nao depende do CSRF nessa rota, mas da validacao da assinatura do webhook.


9. Explicando a sintaxe de models

No Django, um model e uma classe Python que herda de "models.Model".

Exemplo:

class Pergunta(models.Model):

Explicacao:

- "class" define uma classe
- "Pergunta" e o nome do model
- "(models.Model)" indica que essa classe vira uma tabela do banco

Campos do model usam sintaxe como:

pergunta = models.TextField()
alternativa_a = models.CharField(max_length=200)
resposta_correta = models.CharField(max_length=1, choices=OPCOES_RESPOSTA)

Explicando:

- "TextField()" guarda texto longo
- "CharField(max_length=200)" guarda texto curto com limite de tamanho
- "choices=..." restringe os valores permitidos

Outro exemplo importante:

usuario = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    on_delete=models.SET_NULL,
    null=True,
    blank=True,
    related_name="partidas_quiz",
)

Explicacao tecnica:

- "ForeignKey" cria relacao entre tabelas
- aqui, "Partida" aponta para o usuario do Django
- "on_delete=models.SET_NULL" significa que, se o usuario for removido, o campo vira nulo em vez de apagar a partida
- "null=True" permite valor nulo no banco
- "blank=True" permite campo vazio em formularios
- "related_name" cria o nome reverso da relacao

Na pratica, isso permite acessar:
- partida.usuario
- usuario.partidas_quiz.all()


10. Explicando tipos de campo usados no projeto

Alguns tipos importantes que aparecem no seu codigo:

- models.TextField()
  Texto maior, como enunciado de pergunta

- models.CharField(max_length=...)
  Texto curto, como serie, materia ou slug

- models.BooleanField(default=False)
  Verdadeiro ou falso

- models.PositiveIntegerField()
  Numero inteiro nao negativo

- models.PositiveSmallIntegerField()
  Inteiro positivo menor, usado para contadores

- models.DateTimeField(auto_now_add=True)
  Data/hora preenchida automaticamente na criacao

- models.DateTimeField(auto_now=True)
  Atualizada automaticamente a cada save

- models.JSONField(default=list ou default=dict)
  Guarda estrutura JSON no banco
  No seu projeto, isso foi usado para temas liberados e payloads de pagamento

- models.DecimalField(max_digits=10, decimal_places=2)
  Numero decimal apropriado para dinheiro


11. Explicando methods dentro dos models

Seus models nao guardam so campos. Eles tambem guardam comportamento.

Exemplo em "PerfilUsuario":

def ativar_tema(self, slug):

Explicacao:

- "self" representa a instancia atual do objeto
- esse metodo opera sobre o proprio perfil

12. Explicando o ORM e as consultas

O Django usa ORM, que significa Object Relational Mapping.
Em vez de escrever SQL puro o tempo todo, voce escreve consultas em Python.

Exemplo real do ranking:

Partida.objects.filter(
    status=Partida.STATUS_FINALIZADA,
    usuario__isnull=False,
    encerrada_em__gte=inicio_periodo,
)

Explicacao da sintaxe:

- "Partida.objects" acessa o manager padrao do model
- ".filter(...)" aplica filtros
- "usuario__isnull=False" significa "usuario nao nulo"
- "encerrada_em__gte=inicio_periodo" significa "encerrada_em maior ou igual a inicio_periodo"

O "__" em Django e usado para:
- fazer lookup em campos
- atravessar relacoes
- aplicar operadores

Exemplos:

- usuario__username
  acessa o username atraves da relacao com usuario

- encerrada_em__gte
  aplica operador "greater than or equal"

Depois disso, o ranking usa:

.values("usuario_id", "usuario__username")
.annotate(
    total_pontos=Sum("pontuacao_total"),
    total_acertos=Sum("acertos"),
    partidas_jogadas=Count("id"),
)

Explicacao:

- ".values(...)" transforma o resultado em dicionarios
- ".annotate(...)" cria agregacoes calculadas
- "Sum(...)" soma valores
- "Count(...)" conta registros

Isso equivale a uma consulta SQL agregada, mas escrita em sintaxe Python do Django.


13. Como a sessao e usada no jogo

Nem tudo no projeto vai direto para o banco.
O estado da partida em andamento fica na sessao:

request.session[QUIZ_SESSION_KEY] = {
    "queue": ids[:TOTAL_PERGUNTAS],
    "answered_count": 0,
    "score": 0,
    ...
}

Explicacao:

- "request.session" e um armazenamento ligado ao navegador do usuario
- ele persiste entre uma requisicao e outra
- aqui ele guarda o estado temporario do jogo

Por que isso foi uma boa escolha?

- evita salvar no banco a cada pequeno passo do jogo sem necessidade
- permite continuar a rodada entre paginas
- mantem o estado temporario separado do historico final

Depois, quando a resposta e confirmada, o sistema tambem registra no banco para historico.


14. Como a autenticacao local funciona

O login tradicional usa recursos nativos do Django:

from django.contrib.auth import authenticate, login as auth_login

Fluxo tecnico:

1. O formulario envia username e password.
2. A view chama:

   user = authenticate(request, username=username, password=password)

3. Se o usuario existir e a senha estiver correta:

   auth_login(request, user)

4. O Django cria a sessao autenticada do usuario.

Assim, em outras views, da para verificar:

if request.user.is_authenticated:

Essa propriedade indica se o usuario esta logado.

INSTALLED_APPS = [

Explicacao:

AUTHENTICATION_BACKENDS = [

    'allauth.account.auth_backends.AuthenticationBackend',

Isso diz ao Django quais mecanismos de autenticacao estao disponiveis.

Outro ponto importante:

if GOOGLE_LOGIN_ENABLED:

        'secret': GOOGLE_CLIENT_SECRET,
        'key': '',

Significado:

16. Como os templates funcionam

Os templates ficam em "quiz/templates/".
Eles sao HTML com marcacoes do motor de template do Django.

Mesmo sem abrir todos aqui, a ideia tecnica e:
- o backend envia um "context"
- o template usa esse contexto para renderizar dados dinamicos

Exemplo conceitual de sintaxe Django Template:

{{ variavel }}
{% if condicao %}
{% for item in lista %}

Explicacao:

- "{{ ... }}" imprime valor
- "{% if ... %}" cria condicional
- "{% for ... %}" cria repeticao

Ou seja, o HTML nao e totalmente estatico. Ele e montado no servidor com dados do Python.


17. Como os temas foram modelados

O arquivo "quiz/themes.py" usa:

from dataclasses import dataclass

e define:

@dataclass(frozen=True)

Explicacao tecnica:

- "dataclass" reduz codigo repetitivo para classes de dados
- "frozen=True" torna os objetos imutaveis depois de criados

Cada tema guarda:
- slug

Isso significa que os temas disponiveis nao estao no banco; eles estao definidos em codigo.

21. Como as migrations entram no projeto

Toda vez que um model muda, o Django precisa refletir isso no banco.
Para isso existem as migrations.

A pasta:

- quiz/migrations/

guarda arquivos Python que representam a evolucao estrutural do banco.

Fluxo tipico:

1. voce altera models.py
2. roda:

   python manage.py makemigrations

3. o Django gera arquivos de migration
4. depois voce roda:

   python manage.py migrate

5. o banco e atualizado

Isso e importante em apresentacao porque mostra controle de versao da estrutura do banco.
